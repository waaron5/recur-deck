# 07: Render and inspect loop

**What to build:** No deck is delivered unseen. After the file is built, the run renders slides 1–3 to images inside the sandbox and the model looks at them, checking for text that overflows, is clipped, overlaps something, or is illegible, and for logos that landed wrong. What it finds goes back as a text fix — shorter copy, never smaller type — and the slide is rebuilt and re-rendered.

The build also gets its structural check before rendering: exactly nine slides, slides 4–9 present and in order, speaker notes present on slides 1–3, and the file reopens cleanly after being written.

The rendering toolchain substitutes metric-compatible fonts for the deck's typeface, which is why the deck is built in a typeface those substitutes match: the rendered image predicts where PowerPoint will break lines. Rendering takes about two seconds, so this is a routine part of every run, not an exception.

Decisions this implements: stages 6 and 7 of [Define unattended generation and failure behavior](../../recur-sell-deck/issues/07-define-unattended-run.md), the render-check availability established in [Verify the selected account's execution and file capabilities](../../recur-sell-deck/issues/09-verify-account-capabilities.md), and the render-check-last collision rule in [Choose the market-map chart treatment](../../recur-sell-deck/issues/10-prototype-market-map-chart.md).

## Comments

**The declared typeface carries no Latin glyphs.** Found September 17, 2026 while
building ticket 06's pre-render fit estimate. Flagged here rather than fixed,
because this ticket owns the render loop and the "ship the font" question.

`design.js` sets `FONT = 'Noto Sans Arabic Light'`, established in
[ticket 01](01-package-skeleton-nine-slide-deck.md) by reading it off the
original presentation. That face contains **no Latin letters** - no `A-Z`, no
`a-z`, in Light, Regular or Bold. It cannot draw this deck's English copy. A
fallback font draws it instead, in the sandbox renderer and in PowerPoint alike,
including on Recur's own machines.

That voids this ticket's third paragraph: the deck is *not* built in a typeface
the render substitutes match, so a render cannot predict PowerPoint's line
breaks by that route. Bundling the OFL font, which ticket 01 left open to this
ticket, would not fix it either - the bundled file has no Latin to render.

Which font actually draws the reference deck's Latin was settled by measurement,
against the reference PNGs:

| Sample | `design.js` records | Arial metrics imply | Error |
| --- | --- | --- | --- |
| Cover name `USFleetTracking` | 27.4pt | 27.30pt regular | -0.4% |
| Thesis title | 20pt | 19.56pt regular | -2.2% |
| Thesis bullet | 11.5pt | 11.35pt regular | -1.3% |
| Bold section label | 15pt bold | 15.10pt bold | +0.7% |

Every sample reads slightly under prediction, which is the expected bias:
measured ink stops at the last glyph's ink while an advance includes its right
side bearing. The match discriminates - Verdana lands 9% wide, Tahoma 4% narrow,
Arial Narrow 18% narrow. Arial is also metric-compatible with the renderer's
Liberation Sans.

Ticket 06's fit estimate therefore measures Arial, generated by
`scripts/derive-font-metrics.js` into `skill/src/font-advances.js`. Reproduce
the finding with:

```
node scripts/derive-font-metrics.js
```

**What this ticket still has to decide:** whether `FONT` keeps naming a face that
cannot render the deck, or changes to the Latin face that actually draws it. The
cover and title geometry were matched to the reference by cap height, which is
within 1.5% across Noto, Arial and Tahoma alike, so that measurement does not
settle it. Someone should open a built deck in real PowerPoint and see which
face it substitutes.
